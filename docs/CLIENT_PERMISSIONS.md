# Nivelle Link 클라이언트 권한 모델

## 권한의 소유자

Nivelle Link가 로컬 PC 접근의 최종 권한자다. LLM은 호출을 제안하고 Nivelle Core는
공유 규칙을 검증하지만, 두 구성 요소 모두 Link의 deny, 비활성화, 루트 제한, 앱
레지스트리 또는 사용자 승인을 넓힐 수 없다.

다음 입력은 권한 출처가 아니다.

- 일반 채팅 텍스트
- Persona와 장기 기억
- 파일 내용과 파일명
- 창/프로세스 제목
- 도구 결과
- Core가 보낸 요약 또는 “사전 검증됨” 표시

권한을 부여할 수 있는 출처는 사용자가 로컬 Nivelle Link 승인 UI에서 한 명시적 결정뿐이다.

## 로컬 정책

정책 모델은 `AgentPolicy`이며 `agent-policy.json`에 원자적으로 저장된다. 알 수 없는 필드는
거부한다. 기본값은 안전하게 닫혀 있다.

| 항목 | 초기값/의미 |
| --- | --- |
| `agent_enabled` | `false`; 전역 실행 차단 |
| `enabled_tools` | `get_system_status`만 포함 |
| `applications` | 비어 있음; 임의 앱 실행 불가 |
| `filesystem_roots` | 비어 있음; 임의 파일 접근 불가 |
| `denied_paths` | 추가 로컬 deny 경로 |
| hidden/system 파일 | 모두 차단 |
| network path | 차단 |
| reparse point | 차단 |
| direct path | 차단; `path_ref` 우선 |
| 세션 승인 TTL | 3,600초 |
| 영구 승인 가능 도구 | `open_application`, `open_folder` |
| 감사/멱등성 보존 | 각 최대 1,000개 기본값 |

각 파일시스템 루트는 별도로 `allow_search`, `allow_read`, `allow_open_folder` 권한을 가진다.
하나를 허용했다고 나머지가 자동으로 허용되지 않는다. 각 등록 애플리케이션은 사용자가
정한 ID, 표시명, 실행 파일 경로와 활성 상태를 가진다.

정책 JSON에는 인증 토큰이나 자격 증명 필드가 없다. Core 관리 화면도 로컬 허용 목록을
수정할 수 없고 상태만 표시해야 한다.

## 승인 모드

| 모드 | 범위 | 저장/만료 |
| --- | --- | --- |
| `deny` | 해당 호출 거부 | 호출 상태에 남김 |
| `allow_once` | 정확히 한 호출 | 1회 사용 후 소진; 동일 replay만 결과 재사용 가능 |
| `allow_session` | 정확한 클라이언트 세션과 범위 | 세션 ID와 TTL에 결합 |
| `allow_always_exact` | 정확한 대상과 인자 범위 | 철회 또는 정책 변경까지; 허용 도구에만 사용 |
| `not_required` | `SAFE_STATUS`의 로컬 활성 도구 | 별도 grant 없음 |

영구 승인은 클라이언트 ID, 도구명·버전, 정확한 대상, 정규화된 전체 인자 hash, 정책 버전과
정책 전체 fingerprint에 결합된다. 실행 경로나 인자, 스키마 또는 정책이 바뀌면 기존 승인은
일치하지 않는다.

세션 승인은 현재 `target_session_id`와 만료 시각이 모두 일치해야 한다. 새 연결은 새
세션이므로 이전 세션 승인을 사용할 수 없다. 모든 저장 승인은 Nivelle Agent 관리 화면에서
철회할 수 있어야 한다.

## 위험 등급별 정책

### `SAFE_STATUS`

활성화된 `get_system_status`는 per-call 승인 없이 실행할 수 있다. 환경 변수, 토큰, 전체
프로세스 목록, 명령줄, 클립보드와 문서 내용은 결과에 포함하지 않는다.

### `LOCAL_READ`

활성 창 메타데이터, 파일명 검색과 텍스트 읽기는 개인정보를 드러낼 수 있으므로 로컬
승인이 필요하다. `read_text_file`은 Phase 3에서 임의 파일에 대한 영구 승인을 지원하지
않는다.

### `INTERACTIVE`

애플리케이션과 폴더 열기는 화면에 보이는 동작을 발생시키므로 기본적으로 한 번 승인이
필요하다. 영구 승인은 등록 `application_id` 또는 canonical exact folder와 전체 인자
범위가 동일할 때만 가능하다.

### `LOCAL_WRITE`

노트와 알림은 애플리케이션 소유 저장소에 새 항목만 생성한다. 삭제, 덮어쓰기와 임의
목적지는 없다. Phase 3 정책상 매번 승인해야 하며 세션·영구 승인으로 넓혀서는 안 된다.

### `UNSUPPORTED_DANGEROUS`

셸, 스크립트 실행, 삭제, 덮어쓰기, 프로세스·레지스트리·서비스 제어는 등록 대상이 아니며
항상 거부한다.

## 실행 전 권한 판정 순서

Link는 부작용 전에 다음 순서로 검사한다.

1. 공유 `ToolRequest`와 해당 도구 인자 스키마를 다시 검증한다.
2. `target_client_id`와 현재 Link ID가 같은지 확인한다.
3. `target_session_id`와 현재 연결 세션이 같은지 확인한다.
4. Agent 전역 활성화와 도구별 활성화를 확인한다.
5. 요청 위험 등급, 도구 버전과 제한 시간이 레지스트리와 일치하는지 확인한다.
6. 승인 불필요 도구가 아니면 로컬 승인 기록을 검색한다.
7. 승인 ID, 대상, 인자 hash, 정책 fingerprint, 세션, TTL과 남은 사용 횟수를 확인한다.
8. 파일 루트/앱 ID 등 도구 고유 정책을 다시 검증한다.
9. 부작용 도구는 멱등성 pending 기록을 먼저 영속화한다.
10. 등록 구현 하나만 호출하고 결과를 다시 스키마 검증한다.

어느 단계에서든 실패하면 이후 단계와 로컬 부작용은 실행하지 않는다.

## 저장과 개인정보 보호

- `agent-approvals.json`에는 멱등성 키 원문 대신 hash를 저장한다.
- 정책 전체 fingerprint와 정규화된 인자 scope hash로 승인 확대를 막는다.
- `agent-audit.json`은 content, reminder text, token/secret/password 계열 값을 제거하거나
  hash로 대체한다.
- 전체 경로와 실행 파일 경로는 로컬 감사에서 hash 요약으로 저장한다.
- Core에는 구조화 원문 대신 제한된 인자/결과 요약만 저장한다.
- 파일 내용과 승인 미리보기 원문은 운영 로그에 기록하지 않는다.

## 관리 화면

싱글턴 Nivelle Agent 창은 개요, 도구, 애플리케이션, 파일시스템, 승인과 감사를 표시한다.
Agent 활성화, 새로고침과 승인 철회 signal이 정의되어 있다. 인증 토큰처럼 알려지지 않은
필드는 표 렌더링 대상에 포함하지 않는다.

Nivelle Core의 Agent 페이지는 orchestration 상태, registry, capability와 통계만 보여야
한다. Core는 Link의 로컬 애플리케이션/파일시스템 허용 목록과 승인 정책을 편집하지 않는다.

## 현재 구현에서 반드시 확인할 릴리스 게이트

다음 항목은 단위 모델이 존재한다는 사실만으로 완료로 간주하지 않는다.

- `LOCAL_WRITE` 요청에 `allow_session`과 `allow_always_exact`가 UI와 로컬
  `ApprovalManager` 양쪽에서 모두 거부되는가
- 위험한 셸·스크립트 호스트·설치 프로그램이 앱 레지스트리에 추가되거나 실행되지 않는가
- 정책 변경 직후 기존 승인이 실제 연결 경로에서 무효화되는가
- 연결 해제 시 세션 승인과 대기 승인이 만료되고 새 세션에 재사용되지 않는가
- 철회 직후 이미 대기 중인 호출이 실행되지 않는가
- 승인 UI가 표시한 정확한 값과 실행 직전 검증한 값이 같은가
- Core 또는 모델이 보낸 approval ID만으로 로컬 grant가 생성되지 않는가

특히 현재 `ApprovalManager`와 카드의 방어를 함께 검증해야 한다. 한 계층이 잘못된 모드를
전달하더라도 다른 계층이 쓰기 승인을 넓히지 않아야 한다.
